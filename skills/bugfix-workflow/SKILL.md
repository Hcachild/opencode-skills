# Bug 修复通用工作流

> 生产环境发现 Bug 时的标准修复流程。适用于所有类型的 Bug：功能异常、输出错误、性能问题、安全漏洞、用户体验问题等。先探索清楚再动手，改最小范围，验证收敛后交付。

## 工作流总览

```
Bug 发现 → 问题定义 → 深度探索（链路追踪）→ 根因定位 → 影响评估
→ 切 hotfix 分支 → 最小核心修复 → 提交 → 验证 → Push → PR → 合并后清理
```

---

## 第一步：Bug 发现与问题定义

### 1.1 收集 Bug 样本

要求用户提供或从日志/监控中提取**完整的 Bug 复现场景**：

- **输入**：用户做了什么操作 / 发了什么消息 / 触发了什么条件
- **预期**：正常应该发生什么
- **实际**：实际发生了什么（完整输出/报错/截图）
- **环境**：哪个服务、哪个环境（生产/预发/本地）、什么时间

### 1.2 界定问题边界

从 Bug 样本中明确：

| 维度 | 要回答的问题 |
|------|------------|
| **现象** | 用户看到的具体异常是什么？ |
| **触发条件** | 什么输入/条件下必现或偶发？ |
| **影响范围** | 影响哪些用户/功能/流程？是否阻断核心业务？ |
| **严重程度** | P0（阻断）/ P1（严重）/ P2（一般）/ P3（轻微） |

### 1.3 定义收敛标准

与用户确认验证方式：

- **验证手段**：单元测试 / 接口调用 / N 次批量对话 / 人工走查
- **验证范围**：覆盖哪些场景和边界条件
- **收敛判据**：N 次全部通过 / 无复现即收敛
- **是否需要回归**：改动是否可能影响其他功能，需不需要回归测试

---

## 第二步：深度探索 — 链路追踪

### 2.1 梳理调用链路

从外到内逐层确认完整调用路径，画出（或写清楚）数据流：

```
用户输入
  → 入口层（API / MCP / Web）
    → 编排层（Agent / Service / Controller）
      → 工具/业务层（Tool / Domain Service）
        → 数据层（DB / Cache / External API）
```

**目标**：确认 Bug 发生在哪一层，数据在层与层之间传递时哪里出了问题。

### 2.2 逆向追踪根因

从 Bug 现象出发，逆向追踪到代码级别：

1. **定位异常输出来源**：Bug 现象中的错误内容，是哪段代码生成/输出的？全局搜索关键词
2. **追踪数据来源**：生成错误内容的代码读取了什么数据？数据从哪里来？
3. **定位逻辑分支**：什么条件导致了走了错误的分支？是数据问题还是逻辑问题？
4. **确认根因行**：找到导致 Bug 的**那一行或那几行代码**

### 2.3 关键检查项

- [ ] Bug 现象中的异常内容在代码库中的来源已定位
- [ ] 完整的数据传递路径已梳理（从输入到输出）
- [ ] 根因已定位到具体函数和代码行
- [ ] 已确认是逻辑错误 / 数据错误 / 配置错误 / 缺失处理
- [ ] 已检查是否存在已有的修复/过滤机制（如果有，为什么没生效）
- [ ] 已确认上游调用方是否有责任（传入了错误数据 vs 本层处理有误）

---

## 第三步：根因定位与责任归属

### 3.1 根因分类

| 根因类型 | 典型表现 | 修复策略 |
|---------|---------|---------|
| **逻辑错误** | 代码分支条件写反、边界判断缺失、类型转换错误 | 修正逻辑分支/条件 |
| **数据错误** | 数据库脏数据、配置错误、上游传入非法值 | 修正数据源头 + 加输入校验 |
| **缺失处理** | 未处理的空值/异常/边界情况、缺少默认值 | 补充缺失的处理逻辑 |
| **输出未脱敏** | 内部字段/枚举/调试信息泄露到用户可见输出 | 在输出层做映射/过滤 |
| **并发/时序** | 竞态条件、缓存过期、异步顺序错误 | 加锁/调整时序/刷新缓存 |
| **配置/环境** | 环境变量错误、依赖版本不兼容、部署配置遗漏 | 修正配置 |

### 3.2 责任归属

判断 Bug 的主要责任在哪一层：

- **Bug 诞生层**：产生错误数据/错误逻辑/错误输出的那一层 → **主要修复对象**
- **Bug 放行层**：本应拦截但没有拦截的那一层 → **评估是否需要加固**
- **Bug 暴露层**：用户看到 Bug 的那一层 → 通常不是修复对象

**原则**：修复诞生层是根本，是否加固放行层取决于影响评估和收敛验证结果。

## 第四步：影响评估

**在动手修改前，必须完成影响面分析。不能跳过这一步直接改代码。**

### 4.1 分析范围

对计划修改的函数/文件，逐维度检查：

| 维度 | 检查内容 | 方法 |
|------|---------|------|
| **调用方** | 谁调用了要改的函数？改了之后对调用方有什么影响？ | 全局搜索函数名 |
| **数据流** | 修改的函数在数据管道中的位置？上下游谁依赖它的输出？ | 追踪返回值的传递链 |
| **副作用** | 函数是否有副作用（写 DB/缓存/文件/全局状态）？修改是否影响副作用？ | 检查函数内部操作 |
| **并行路径** | 是否存在另一条代码路径也能到达同样的输出？改了这条，那条是否也需要改？ | 搜索同类逻辑 |
| **现有测试** | 是否有测试覆盖了要改的函数？改了之后测试是否会断？ | 搜索 `tests/` 目录 |
| **配置/环境** | 修改是否依赖特定的环境配置？部署时是否需要额外操作？ | 检查配置文件和部署脚本 |

### 4.2 安全判据

只有满足以下全部条件，才认为修改是安全的：

- [ ] 改动范围已明确界定，不会产生意料之外的副作用
- [ ] 上下游依赖的数据流不受影响（或影响已评估安全）
- [ ] 现有测试不会因修改而失败（或已确认需要同步更新测试）
- [ ] 新增的函数/变量名在代码库中无冲突
- [ ] 修改有合理的兜底/默认值处理（不会因边界情况产生新 Bug）
- [ ] 不引入新的安全问题（如注入、信息泄露、权限绕过）

### 4.3 如果不安全

如果影响评估发现修改不安全（影响面过大/有不可控副作用），则：
1. 重新评估修复方案，考虑更小范围的改动
2. 或拆分为多个小改动，分步修复
3. 或与用户讨论是否接受当前方案的风险

---

## 第五步：最小核心修复

### 5.1 原则

- **最小改动**：只改 Bug 的直接根因，不做无关重构、不加未经验证的防御层
- **先验证再扩展**：先做最小修复，验证收敛后如果没问题就不再追加改动
- **精准手术**：改最少的代码行，解决最核心的问题
- **可回退**：改动应该足够小，如果引入新问题可以快速回退

### 5.2 分支规范

```
分支名: hotfix/<scope>-<problem-description-en>
基线:   从 main 切出
```

示例：
```
hotfix/compliance-match-type-terminology-leak
hotfix/mcp-knowledge-chat-payload-dedup
hotfix/llm-wiki-empty-assistant-before-tool
```

### 5.3 Commit 规范

```
fix(<scope>): <中文问题描述>

<scope> 规则：
- 修改提示词 → fix(prompt)
- 修改代码工具（如合规） → fix(compliance)
- 修改检索逻辑 → fix(retrieval)
- 修改 MCP 层 → fix(mcp)
- 修改部署配置 → fix(deploy)
- 修改 API 层 → fix(api)
- 修改数据库/迁移 → fix(db)
```

示例：
```
fix(compliance): 合规工具match_type技术枚举泄露给LLM导致用户回答出现专有名词
```

### 5.4 修改前确认

动手写代码前，向自己确认：
1. 我要改哪个文件的哪几行？
2. 这个改动会影响哪些其他代码路径？
3. 改完之后怎么验证？
4. 如果这个改动有问题，怎么回退？

## 第六步：验证

### 6.1 确认代码已生效

- 如果服务是 reload 模式，确认改动已被加载（等几秒或重启）
- 如果是编译型语言，确认已重新编译
- 用最简单的方式确认：直接调用出 Bug 的接口/功能，看是否已修复

### 6.2 精准验证（快速）

直接复现 Bug 的最小条件，确认 Bug 已消失：

```python
# 示例：直接调用出 Bug 的 API，检查返回是否正常
payload = {"message": "压缩机能不能走SN318发美国"}
resp = call_api(payload)
content = resp["content"]
assert <Bug 现象不再出现>
```

### 6.3 批量验证（收敛测试）

通过循环调用 N 次（如 100 次），覆盖多种业务场景，确认修复稳定：

**验证脚本设计要点**：

1. **输入池**：准备 20-50 个不同的输入，覆盖：
   - 触发 Bug 的原始输入
   - 同类问题的不同变体
   - 边界条件（空输入、超长输入、特殊字符等）
   - 不应受影响的正常场景（回归检查）
2. **检查规则**：对每次返回结果执行断言检查（精确匹配 / 正则 / 语义判断）
3. **随机选取**：每轮从输入池随机选一个，模拟真实用户行为
4. **结果统计**：记录 Passed / Failed / Skipped
5. **失败详情**：如有失败，输出失败的输入和具体异常

**收敛判据**：
- N 次全部 PASS → 修复稳定收敛，可以交付
- 任何一次 FAIL → 分析失败原因，评估是否需要追加修复

### 6.4 验证脚本模板

```python
"""
N-round verification for bug fix.
"""
import json, random, sys, time, urllib.request

API_URL = "http://127.0.0.1:8000/api/v1/llm-wiki/chat"  # 按实际改
TOTAL_ROUNDS = 100
TIMEOUT = 90

# Bug 检查规则：根据具体 Bug 定义
def check_bug_absent(content: str) -> list[str]:
    """返回内容中仍存在的 Bug 痕迹列表，空列表表示通过。"""
    problems = []
    # 示例：检查是否包含不应出现的技术术语
    blacklist = ["rule_product_name_exact", "match_type"]
    for term in blacklist:
        if term in content:
            problems.append(term)
    return problems

# 输入池：覆盖 Bug 触发场景 + 回归场景
INPUTS = [
    "压缩机能不能走SN318发美国",
    "除湿机能不能走SN318发美国",
    # ... 覆盖多种场景
]

failures = []
skipped = []

for i in range(1, TOTAL_ROUNDS + 1):
    question = random.choice(INPUTS)
    payload = json.dumps({"message": question}).encode("utf-8")
    try:
        req = urllib.request.Request(API_URL, data=payload,
            headers={"Content-Type": "application/json; charset=utf-8"})
        resp = urllib.request.urlopen(req, timeout=TIMEOUT)
        data = json.loads(resp.read().decode("utf-8"))
        content = (data.get("assistant_message") or {}).get("content", "")
        if not content.strip():
            skipped.append((i, question, "empty"))
            continue
        problems = check_bug_absent(content)
        if problems:
            failures.append((i, question, problems))
            print(f"  [{i:3d}/{TOTAL_ROUNDS}] FAIL  Q: {question[:40]}")
        else:
            print(f"  [{i:3d}/{TOTAL_ROUNDS}] PASS  Q: {question[:40]}")
    except Exception as e:
        skipped.append((i, question, str(e)))

print(f"\nPassed: {TOTAL_ROUNDS - len(failures) - len(skipped)}")
print(f"Failed: {len(failures)}")
print(f"Skipped: {len(skipped)}")
if not failures:
    print("RESULT: ALL PASSED - fix is stable and converged.")
```

## 第七步：Push 与 PR

### 7.1 Push

```bash
git push -u origin hotfix/<branch-name>
```

### 7.2 创建 PR

```bash
gh pr create \
  --base main \
  --head hotfix/<branch-name> \
  --title "fix(<scope>): <中文问题描述>" \
  --body-file pr_body.md
```

### 7.3 PR Body 模板

```markdown
## 问题
<Bug 现象原文，含输入/预期/实际>

## 根因
<链路追踪结论，从 Bug 诞生点到暴露点的完整路径>

## 修复
<改动内容：改了哪些文件、新增了什么、改了哪行、为什么这样改>

## 影响面
<逐维度分析结论，确认不影响其他功能>

## 验证
<N 次验证结果，Passed/Failed/Skipped 统计>
```

### 7.4 合并后清理

PR 合并到 `main` 后：

```bash
git checkout main
git pull origin main
git branch -d hotfix/<branch-name>
git push origin --delete hotfix/<branch-name>
```

## 决策树

```
发现 Bug
  │
  ├─ 能否复现并定位到具体代码行？
  │    ├─ 是 → 继续
  │    └─ 否 → 回到第二步深度探索
  │
  ├─ 影响评估是否安全？
  │    ├─ 是 → 继续
  │    └─ 否 → 重新评估修复方案，考虑缩小范围或分步修复
  │
  ├─ 执行最小核心修复
  │
  ├─ 精准验证通过？
  │    ├─ 是 → 继续
  │    └─ 否 → 检查代码是否生效 / 修复是否正确
  │
  ├─ N 次批量验证全部通过？
  │    ├─ 是 → 修复收敛，Push + PR，结束
  │    └─ 否 → 分析失败原因，追加修复，重新验证
  │
  └─ 结束
```

## 检查清单

### 探索阶段
- [ ] 收集完整 Bug 样本（输入/预期/实际/环境）
- [ ] 界定问题边界（现象/触发条件/影响范围/严重程度）
- [ ] 梳理完整调用链路（从入口到数据层）
- [ ] 定位根因到具体函数和代码行
- [ ] 确认是逻辑错误/数据错误/缺失处理/输出未脱敏/并发/配置
- [ ] 检查是否存在已有的修复/过滤机制（如果有，为什么没生效）

### 影响评估阶段
- [ ] 搜索改动函数的所有调用方
- [ ] 确认数据流上下游不受影响
- [ ] 确认无意外副作用（DB/缓存/全局状态）
- [ ] 确认并行路径是否需要同步修改
- [ ] 确认现有测试是否会断
- [ ] 确认新增函数/变量名无冲突
- [ ] 确认不引入新的安全问题

### 修复阶段
- [ ] 从 main 切 hotfix 分支（命名: `hotfix/<scope>-<problem-en>`）
- [ ] 改动范围最小化（只改根因，不重构）
- [ ] 有合理的兜底/默认值处理
- [ ] Commit 符合 `fix(scope): 中文描述` 规范

### 验证阶段
- [ ] 确认服务已加载新代码（reload/重启）
- [ ] 精准验证通过（直接复现 Bug 条件，确认已消失）
- [ ] N 次批量验证全部 PASS（覆盖多种场景 + 回归检查）
- [ ] 如有 FAIL，分析原因并追加修复

### 交付阶段
- [ ] Push 到 origin
- [ ] 创建 PR（base: main）
- [ ] PR Body 包含问题/根因/修复/影响面/验证
- [ ] 合并后清理本地和远程 hotfix 分支

## 附录：Bug 类型速查

不同类型的 Bug 在"根因定位"和"修复策略"上有差异，参考下表快速对号入座：

| Bug 类型 | 根因定位方法 | 修复策略 | 验证重点 |
|---------|------------|---------|---------|
| **输出内容错误**（如术语泄露、数据错误） | 搜索异常输出内容在代码中的生成位置，追踪数据来源 | 在输出层做映射/过滤/修正 | 黑名单匹配 + N 次批量验证 |
| **功能不工作**（如工具不调用、流程中断） | 从入口追踪执行路径，定位中断点 | 修正中断条件/补全缺失逻辑 | 复现场景 + 回归不受影响的功能 |
| **性能问题**（如超时、慢查询） | 分析耗时分布（日志/Profile），定位瓶颈 | 优化查询/加缓存/减少调用 | 耗时对比 + 压力测试 |
| **并发问题**（如竞态、死锁） | 分析时序和共享状态，定位竞态窗口 | 加锁/调整时序/消除共享状态 | 并发压测 + 长时间运行验证 |
| **配置/环境问题** | 对比正常环境与异常环境的配置差异 | 修正配置/补充缺失配置 | 部署后验证 + 多环境对比 |
