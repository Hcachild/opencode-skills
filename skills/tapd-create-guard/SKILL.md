## 铁律（不可绕过）

**只要用户要求创建 TAPD 工作项（单个 / 批量 / 复制，含缺陷 Bug），必须在调用创建接口之前先跑本技能校验。缺任一必填字段 → 不得创建；正确做法是：先按最佳理解把该字段填成一版草稿（标注来源与「建议」），连同其余字段一次性给用户确认，用户确认或改后再建。不允许"先建后补"或"边建边提醒"。**

**层级铁律（同属不可绕过）：Task 的父需求只能是 Story，Story 的父需求只能是 Feature，Feature 的父需求只能是 Epic；Epic 无父需求。严禁同级挂载（Story→Story / Task→Task）与越级挂载 —— 违反即不得创建。**

**确认铁律（同属不可绕过）：Epic / Feature / Story / Task / 缺陷（Bug）五类都要先出一版完整草稿（含标题、详细描述全文、全部必填字段）给用户「全量确认」；用户改了任何字段 → 全量重展、重新确认；整版全部字段确认通过后才允许创建。**

**配置铁律（同属不可绕过）：TAPD 已配置好的字段名、字段 ID、字段类型、枚举选项一律只读；不得新增 / 改名 / 删除 / 停用枚举值，创建时只能填已存在的选项。**

**流转铁律（同属不可绕过）：变更状态前必须先校验该流转的必填字段 —— 有值的直接带出、没值的先按经验拟建议值，然后「全量展示」给用户确认；确认通过后才允许流转（详见「六、状态流转校验」）。**

**删除铁律（同属不可绕过）：删除 TAPD 任何信息前，必须给出「醒目警告 + 关联影响清单」，经用户明确确认后才可删除；只问一句"要删吗"不算（详见「⛔ 删除保护」）。**

**账号铁律（同属不可绕过）：一切写操作与署名必须使用「授权 TAPD 账号」—— 授权账号**由 `get_current_user` 实时确定，技能不写死姓名**（技能由谁安装使用，其 TAPD API 凭证对应的账号就是授权账号）；不换账号、不冒用他人署名；但业务字段（处理人 / 开发人员 / 需求提出方）按业务实际填，不算冒名（详见「⛔ 授权账号一致性」）。**

**材料铁律（同属不可绕过，2026-10-13 用户要求）：一切写入 TAPD 的信息（字段值、详细描述、评论、工时）必须基于「用户提供的材料」—— 即用户对话中给出的内容、用户指定的文档 / 链接 / 截图、以及 TAPD 里已存在的真实数据。材料之外靠推断 / 联想 / 经验得出的信息（优先级、处理人、时间、枚举取值、描述中的数字与结论等），必须在草稿中标注「建议 / 推断」并全量展示，经用户确认后才能写入。未经用户确认，一律不得对 TAPD 执行任何写操作（创建 / 修改 / 流转 / 删除 / 评论 / 登记工时）。**

## ⛔ 权限校验（创建 / 修改前必读）

**TAPD 的调用权限由「授权用户」（API token 对应的账号）决定。权限不足时，一律停下并按标准话术回复 —— 不得重试、不得换方式绕过。**

### 当前授权用户怎么看

```
mcp__tapd__get_current_user   →   返回 { nick: "<账号昵称>", company_id: "..." }
```

**授权账号不写死姓名** —— 由 `get_current_user` **实时确定**：谁的 TAPD API 凭证配置在当前环境，授权账号就是谁（不同人安装 / 使用本技能，各自是自己的授权账号）。每次写操作前**现查现用**，不要依赖历史记录、文档示例或他人转述里的名字。

### ⚠️ 重要限制：无法在调用前静态判断

TAPD 的**角色 / 权限配置拿不到** —— `get_workspace_users` 只返回成员昵称列表，**不含 `role_id`、也不含任何权限标记**；也没有"某角色能建哪些工作项"的查询接口。

所以**不能**在创建前判定"这个账号能不能建 Epic"。权限校验只能采用下面的方式。

### 校验方式：接口报错 → 标准话术

创建 / 修改 / 删除调用**返回失败**时，先判断是否权限类错误。

**判定依据（按 TAPD 实际情况整理）：**

| 信号 | 算不算权限不足 |
|---|---|
| HTTP **403**、`permission_denied` | ✅ 是（TAPD 权限不足的**主信号**） |
| `permission` / `forbidden` / `denied` / `not allowed` / `unauthorized` / `Authorization` | ✅ 是 |
| 中文：`无权限` / `权限不足` / `没有权限` / `无权` / `不允许` | ✅ 是 |
| `company does not match workspace` | ✅ 是（凭证与目标项目不匹配） |
| HTTP **404** `workspace xxx not existed` | ❌ 不是（项目 ID 错） |
| HTTP **422** | ❌ 不是（参数/必填问题 → 回到必填校验流程处理） |
| HTTP **429 / 500 / 502** | ❌ 不是（频率/服务端问题 → 可稍后重试） |

> 依据：TAPD 官方错误码表（open.tapd.cn）**未单列"权限不足"**，实际以 **HTTP 403 + 响应消息体**体现，消息体里常见 `permission_denied`。别把 404/422 误当权限问题上报。

**命中后：立即停止**（不重试、不换接口、不"先试着建别的"），按场景回复：

| 场景 | 标准话术（照此措辞，不要改写） |
|---|---|
| 创建 | **无法创建，授权用户权限不足，有疑问请联系项目经理** |
| 修改 | **无法修改，授权用户权限不足，有疑问请联系项目经理** |
| 删除 | **无法删除，授权用户权限不足，有疑问请联系项目经理** |

可在话术**之后**附上接口原始报错（便于项目经理排查），但主话术保持上面措辞。

> **缺陷（Bug）同样适用本节全部内容**：`create_bug` / `update_bug` / 缺陷状态流转 / 删除缺陷，权限判定依据与标准话术**与 Epic / Feature / Story / Task 完全一致**（如「无法创建，授权用户权限不足，有疑问请联系项目经理」），不因工作项类型改变措辞。

### 规范层面的角色边界（创建前可做软提醒）

| 工作项 | 规范要求的创建角色 |
|---|---|
| Epic / Feature | **项目经理** |
| Story | **产品经理**（PM 仅特定场景代建） |
| Task | 各角色均可 |
| 缺陷 | **测试** |

若用户要求的操作明显超出角色范围，可**先提醒确认**；但**最终以接口权限为准** —— 提醒不等于拦截，接口报错才拦截。

## ⛔ 已有值 / 自动字段保护（修改前必读）

**铁律：不得随意改动 TAPD 里已经写好值的字段。本节适用于一切修改接口 —— `update_story_or_task` 与 `update_bug`（缺陷修改）同样要先全量确认（缺陷修改专项要求见「Bug（缺陷）」一节）。**

### 1）系统自动写入的字段 —— 一律不手工改

以下字段由**状态流转自动写入**，手工改会污染时效与工时统计：

| 字段 ID | 界面名 | 何时自动写 |
|---|---|---|
| `custom_field_23` | 实际需求评审时间 | 草稿 → 需求评审通过 |
| `custom_field_27` | 实际开发开始时间 | 需求评审通过 → 开发中 |
| `custom_field_25` | 实际提测时间 | 开发中 → 已提测 |
| `custom_field_29` | 实际测试开始时间 | 已提测 → 测试中 |
| `custom_field_26` | 实际测试完成时间 | 测试中 → 测试通过 |
| `custom_field_seven` | 实际上线时间 | 产品验收通过 → 已上线 |
| `effort_completed` | 完成工时 | 登记工时时 |
| `exceed` / `remain` | 超出工时 / 剩余工时 | 由预估与完成工时自动算 |
| `completed` | 完成时间 | 流转到终态时 |

→ **默认不动。** 即使用户要求改，也要先说明"这是系统自动字段，改了会影响统计数据"，确认后才动。

### 2）其他已有值的字段 —— 覆盖前必须确认

- **补空 → 可以**（字段为空，填上值）。例：补 `custom_field_36`；
- **覆盖 → 不行**（字段已有值，要改成别的）。必须先回读当前值、明确告诉用户"**现在是 X，要改成 Y**"，**用户明确确认后**才改；
- **批量改** → 逐条列出来给用户过目，不许"一把梭"。

### 3）改前必做（用脚本，别靠记忆）

任何 `update_story_or_task` / `update_bug` 之前，先跑变更安全校验：

```bash
python "<skill目录>/scripts/update_change_guard.py" \
  --current "<回读的当前数据.json>" --target "<拟修改的数据.json>"
```

输出把每处改动分级：

| 级别 | 含义 | 处理 |
|---|---|---|
| ✅ **OK** | 当前为空 → 补空 | 可直接改 |
| ⚠️ **WARN** | 当前已有值 → 覆盖 | **必须先让用户确认** |
| ⛔ **BLOCK** | 系统自动字段 | **默认不动** |

退出码：`0`=只有补空（可执行）/ `1`=存在覆盖或自动字段（**不得直接执行**）/ `2`=输入错误。

**改动里的枚举字段还要过第二道闸（2026-10-13 用户确认）**：拟写入的枚举值必须属于该空间已配置选项 —— 按「2.5）枚举实时读取」拉取选项核对；**不在选项内（如把严重程度改成 P2）→ 弹出提示、不得执行修改**，让用户从已有选项里挑或由管理员配置新选项。

### 4）禁止的典型行为

- ❌ 为了让数据"整齐"，批量把字段刷成统一值
- ❌ 改 A 字段时顺手把 B、C 也重写一遍（哪怕值相同）
- ❌ 直接覆盖别人填的已有值，事后才说
- ❌ 手工写"实际提测时间"这类系统自动字段

## ⛔ 字段配置 / 枚举值保护（**不得改动 TAPD 已设置好的任何配置**）

> **铁律：TAPD 里已经配置好的「字段名」「字段 ID」「字段类型」「枚举选项」，一律只读使用，不得修改、新增、改名、删除、停用或排序。**

### 1）具体禁止什么

| 对象 | 禁止行为 |
|---|---|
| **字段名 / 字段 ID** | 改名、改 ID、改字段类型、改适用范围 |
| **枚举选项** | 新增选项、改名、删除、停用、调整顺序（如优先级 `P0-P3`、项目分类、分类、需求类型、任务类型、`Epic归属项目或系统` 的 25 项） |
| **必填配置** | 擅自更改某状态流转的必填项（要改请走管理员） |

### 2）创建 / 修改时必须遵守

1. **枚举字段只能填该空间"已配置的选项"** —— **创建和修改都一样**（2026-10-13 用户确认：修改时选了不存在的枚举值同样不允许，必须弹出提示）；不得自造，例如不得写 `P5`、`紧急`、`编码开发`、把严重程度改成 `P2` 这类不存在于配置里的值；
2. **没有合适选项时 → 停下弹出提示报告用户**（例如「取值「P2」不是「严重程度」的已配置选项，可选：致命/严重/一般/提示/建议」），由用户在已配置选项里挑或让管理员在 TAPD 界面配置新选项；**AI 不代劳、不用别的值顶替、不新建同名字段绕过 —— 创建与修改都不得执行**；
3. **自定义字段用 `custom_field_xx` ID 引用**，不改名、不臆造不存在的字段 ID；
4. 技术前提：MCP 本身**没有**字段 / 枚举配置接口（改不了），但**仍禁止用"新建同名自定义字段""拿别的字段凑"等方式绕过**。

### 2.5）枚举实时读取（校验枚举值前先拉取，不要靠手抄清单）

TAPD 字段枚举可能被管理员随时调整（2026-10-13 当天就改过一次），校验创建 / 修改的枚举值时，**优先实时拉取目标空间的最新选项**：

| 接口 | 覆盖范围 | 用法 |
|---|---|---|
| `get_stories_fields_info` | **需求侧一站式**：status（14 态中英映射）、priority（P0-P3）、category_id（含选项 ID）、需求类型、任务类型、项目分类、迭代（含 ID）、标签、阻塞原因、产品价值等级、Epic归属（备注内 25 项）等全部字段候选值 | 直接调，返回按字段名组织的 options |
| `get_entity_custom_fields`（entity_type=bugs） | **缺陷自定义字段**枚举（如 36495762 的所属系统 25 项、问题来源 5 项）+ 字段 ID | 查 options 字段（`\|` 分隔） |
| `get_workflows_status_map` | 状态中英文对照（bug / story 各自 system） | 流转时用 |

**固定枚举（接口级，不随空间配置变）**：缺陷 `severity` = fatal 致命 / serious 严重 / normal 一般 / prompt 提示 / advice 建议（**只收英文值**，传中文 / P1 无效）；需求优先级 priority_label = P0/P1/P2/P3（以实时拉取为准）。

### 3）脚本怎么判

`validate_required_fields.py` 会把取值与该空间**已知的枚举清单**比对：

- 不在清单内 → 默认给**提示**（措辞明确写出"不得新增/改名/删除、只能用已有选项"）；
- 加 `--strict-enum` → 升级为**错误**，直接阻断创建。

**无论哪种模式**：出现"枚举取值未命中""模板不符"提示时，**都必须先与用户确认或改正，不得直接创建**（见「三、执行流程」第 5 步）。

## ⛔ 删除保护（**高危：必须醒目警告 + 关联影响确认**）

> **用户要求（2026-10-13）：删除 TAPD 信息时必须有醒目的提醒文字，并把「删除后的关联影响」列给用户确认，确认通过才能删。**

### 1）绝对禁止

- ❌ 未经用户**明确确认**就调用任何删除接口；
- ❌ 只问一句"要删除吗？"而**不列关联影响**；
- ❌ 批量删除时**不逐条**列影响（一次删多条必须逐条列）；
- ❌ 用"改状态 / 改名 / 移走"变相替代删除来**规避确认**。

### 2）删除前三步（不得跳步）

1. **落盘全量**（确保能算出完整子树；下拉漏了会**低估**影响）；
2. **跑脚本**算影响：

```bash
python "<skill目录>/scripts/delete_guard.py" --id "<拟删 id>" --items "落盘1.json" ["落盘2.json" ...]
```

   输出含：**醒目警告块** + 影响清单（级联删除数/类型、其中已完成数、工时清零、父级汇总变化、上游链路、不可逆风险）+ 将被一并删除的下级明细；

3. **全量展示给用户 + 等明确确认**（见第 3、4 点）→ 确认后才执行删除。

### 3）醒目警告模板（**"不可逆"与"未确认不得删除"两处必须保留**）

```
============================================================
！  警 告 ： 删 除 操 作 不 可 逆  ！
============================================================

拟删除：Story（需求）「【测试】需求A」   ID：…   状态：…   处理人：…

---- 关联影响（必须逐项确认）----
 1. 级联删除：该工作项及其 2 个下级（Task×2）将一并被删除
 2. 其中 2 个下级已「完成」—— 已发生的工作记录会被一并清掉
 3. 工时清零：下级累计预估 12h、完成 11h 将随删除消失，父级汇总同步下降
 4. 父级汇总变化：父级「测试Feature」的工时 / 进度汇总会减少
 5. 上游链路：测试Epic › 测试Feature — 删除后该层级出现缺口
 6. 不可逆风险：即便平台侧可恢复，关联关系、工时与评论也不保证完整还原

---- 将被一并删除的下级（共 2 条）----
 · [Task] 开发-需求A子任务  1300
 · [Task] 测试-需求A子任务  1301

============================================================
请回复明确确认后才可执行删除；未确认前不得删除。
============================================================
```

### 4）什么才算"确认"

- 必须是**明确的删除指令**（如"确认删除 1200"）；含糊的"嗯""看看""知道了"**不算确认**；
- 用户要求先备份 / 先看某条细节 → 先照办，**不要抢先删**；
- 删除后回报："已删除 X（含 N 个下级）"，并提示可在平台回收站尝试找回（以实际版本为准）。

## ⛔ 授权账号一致性（**所有写操作与署名**）

> **用户要求（2026-10-13）：所有操作必须使用授权的 TAPD 账号；评论、姓名等也必须是授权 TAPD 账号的信息。**

### 1）规则

1. **每次写操作前先 `get_current_user` 确认当前授权账号**（以实时返回为准，技能不预设姓名）；身份存疑就停下确认；
2. **不得切换 / 伪造身份** —— 不用他人账号，不在评论里冒用他人署名，不写"某某代发"这类不实署名；
3. **评论署名一律为授权账号本人** —— `create_comments` 的提交人就是授权账号，正文里**不要再挂别人的名字**；
4. **工时登记人同样是授权账号** —— 不要替他人登记工时却不说明。

### 2）必须分清的一点（别把业务字段当"冒名"）

| 类别 | 要求 |
|---|---|
| **操作人 / 评论署名 / 工时登记人** | **必须是授权账号**（即 `get_current_user` 的返回者本人） |
| **业务字段**（`owner` 处理人、`developer` 开发人员、需求提出方…） | **按业务实际填**，可以是别人 —— 这是分工信息，不是冒名 |

> 例：以授权账号创建任务、把「处理人」填成张岩 → ✅ 正常；但在评论里署名"张岩" → ❌ 违规。

### 3）权限报错仍走既有话术

账号无权限时（403 / `permission_denied` / 无权限…）→ **立即停止**，回「无法创建 / 修改 / 删除，授权用户权限不足，有疑问请联系项目经理」。

## 为什么需要这道闸

TAPD 系统本身**只在状态流转时校验必填**（例如任务「未开始 → 进行中」才要求填处理人/优先级/时间等），**创建时并不校验**。通过 MCP / API 创建会绕过这层约束，产生空壳工作项（历史上"知识库 v1.3 那批任务字段全空"就是这么来的）。

本技能在创建前补上这道闸，保证通过 MCP 建出来的工作项一开始就是合规的。

### 层级拍平字段：Epic归属项目或系统（必须自动继承）

**`custom_field_36`（Epic归属项目或系统）** 是**层级拍平字段**，专门用于"按 Epic 汇总工时"（Epic 挂子需求有数量上限，超限时靠这个字段聚合）。

| 对象 | 要求 |
|---|---|
| **Epic** | **创建时必填**（规范要求，见上表） |
| **Feature / Story / Task** | 规范未列为必填，但**必须自动继承父级值** —— 留空会导致工时汇总漏算 |

**继承链路**（逐级往下传）：

```
Epic.custom_field_36
  └─ Feature  ← 取父 Epic 的值

            └─ Task    ← 取父 Story 的值（同理可继续上溯）
```

**创建时的执行要求（必须做）：**

1. 创建 Feature / Story / Task **之前**，先用 `get_stories_or_tasks` 按 `parent_id` 查出父级的 `custom_field_36` 值；

3. 创建后回读确认该字段**非空**；若仍为空（自动化未触发），用 `update_story_or_task` 补上。

**发现存量空缺时的修复（用脚本，不要手算）：**

```bash
python "<skill目录>/scripts/backfill_epic_project_field.py" \
  --items <落盘的TAPD数据.json> [更多分页文件...] --out backfill.json
```

- **输入**：`get_stories_or_tasks` 的落盘 JSON（含 `data[].Story`）；分页拉多次时把多个文件一起传进去，脚本会按 id 去重合并
- **脚本自动完成**：找出 Feature / Story / Task 中 `custom_field_36` 为空的条目 → 沿 `parent_id` 链向上逐级查找**第一个非空值** → 输出「id → 应填值」清单

### 工时登记校验（单人单日合计 >12h → 提示修改 / 分摊，用户坚持则放行）

> **2026-10-13 用户要求**：登记工时（`add_timesheets`，含批量）前，校验**同一登记人（owner）同一花费日期（spentdate）**的合计——「已有工时 + 本次拟登记」**超过 12h → 醒目提示用户需要修改**（减少工时或**分摊到不同日期**）；用户明确坚持原值才可放行（与时间顺序约束同款边界）。

2. **跑校验**：


   输出按「人 + 日期」分组：✅ 正常 / ⚠️ 超限（附明细与分摊建议）；退出码 `0`=不超限 / `1`=有超限 / `2`=输入错误；

### 工时全周期健康检查（某用户近 2 个月超 12h 的全部日期明细，2026-10-13 用户要求固化）

### 第 4 步：校验父需求层级（**铁律，脚本可强制**）

#### 4.1 层级铁律

**父需求只能是"上一级"，严禁同级挂载、越级挂载：**

| 创建对象 | 父需求只能是 | ❌ 不允许 |
|---|---|---|
| **Epic** | 无（顶层） | 挂任何父需求 |
| **Feature** | **Epic**（`0033`） | 挂 Feature / Story / Task |
| **Story** | **Feature**（`0032`） | **挂 Story**（同级）/ 挂 Epic（越级）/ 挂 Task |
| **Task** | **Story**（`0031`） | **挂 Task**（同级）/ 挂 Feature、Epic（越级） |

> **明确禁止的例子**：Story 的父需求是另一个 Story、Task 的父需求是另一个 Task —— 一旦出现即为**错误，不得创建**。

#### 4.2 怎么校验

**① 优先用脚本（传 `parent_type` 即可自动判定）**

在待创建 JSON 里给每条加一个 `parent_type`（可写 `epic/feature/story/task`、中文名「史诗故事 / 特性 / 需求 / 任务」，或直接给父需求的 `workitem_type_id`），第 3 步的脚本会：

- 父需求类型与自身相同 → **错误**（禁止同级挂载）
- 父需求类型 ≠ 上一级 → **错误**（禁止越级 / 挂错层级）
- Epic 带了 `parent_id` → **错误**
- 没传 `parent_type` 且有 `parent_id` → **提示**：请用 MCP 查一次父需求类型

**② 没传 `parent_type` 时，用 MCP 补查**

用 `mcp__tapd__get_stories_or_tasks`（`fields: id,name,workitem_type_id`，按 `id` 查父需求），确认上表的层级正确。

**③ 无论哪种方式，发现层级不对 → 报给用户，不得创建。**

### 第 5 步：先出一版完整草稿给用户确认（**必经，不得跳过**）

> **口径（2026-10-13 用户要求，已由"先追问缺失"改为"先出草稿"）：**
> 不要再一个个问缺什么字段，而是**先按自己对该项目/该空间的历史理解，把这一版完整写出来**给用户看 —— 用户看一眼、确认或改几处，比来回追问省事得多。

#### 5.1 AI 先按最佳理解，把全部必填字段**和详细描述**填成一版草稿

1. **填满，不留空** —— 该类型的**每个必填字段都给一个值**，形成一版"看着就能直接建"的草稿；
2. **标题 + 详细描述由 AI 主动写草稿**（2026-10-13 用户明确要求）—— **不要留空让用户写**：
   - **标题**：按模板写 —— Story `【模块名称】简要描述`；Task `任务类型-动作`；Epic / Feature 写清项目 / 版本名称；**缺陷按目标空间模板**（两空间不同，见「Bug（缺陷）」一节：生产缺陷=`【系统名称】【模块或功能名称】描述`，需求池=`【系统名称 版本号】描述`）；
   - **Story 详细描述**：按四段模板**写全正文** —— 【需求背景】（业务场景与问题 / 影响范围 / 价值）、【需求描述】（面向角色 / 功能点 P0-P2 / 范围边界 ✅❌）、【验收标准】、【附录】；
   - **Task 详细描述**：按三段模板**写全正文** —— 一、任务说明（做什么 / 怎么做）、二、完成定义（DoD）、三、依赖（依赖任务接口 / 阻塞）；
   - 描述要**具体到能直接看懂**，**不许用"详见 PRD""待补充"占位**；实在缺信息的段落，把**段落标题搭好**并在该段标「❓ 待你补充」，而不是整段不写；
   - 描述里若引用量化价值 / 现状数据，**必须标来源**（如"据调研""（测算值）"），不得凭空编造数字；
   - ⚠️ **描述必须写成结构化 HTML，不能只用纯文本换行**（`\n`）—— TAPD 描述是富文本，`\n` 会被**并进同一个 `<p>`**，界面上所有内容挤成一行。**写法见下方「描述结构化写法」**（`<p>` 分段 + `<strong>` 小标题加粗 + `<ul><li>` 分条）。
3. **推断来源要写明** —— 每个值后面标清出处，例如：
   - `父需求`：取自用户给的 Feature / Story ID
   - `Epic归属项目或系统`：按父级 Epic 继承（`custom_field_36`）
   - `优先级`：与同级同类工作项保持一致（默认 `P2`）
   - `处理人 / 项目Owner`：沿用该项目既有负责人
4. **需用户拍板的项也要给建议值，但必须标注「建议」** —— 优先级 / 计划时间 / 处理人 / 分类 / 预估工时等，不再一律空着问，而是**先给一个合理建议并标明是建议**，让用户"不改就过、要改直接说"；其中**人员字段（处理人 / 项目Owner / 开发人员 / 测试人员等）默认填授权账号本人的昵称**（`get_current_user` 实时获取，技能不写死姓名），来源标「授权账号本人（默认，可选改为实际负责人）」（2026-10-13 用户要求）；
5. **实在无从推断的标「❓ 待你给」** —— 如 `Epic归属项目或系统` 这类强业务语义的项，给 **1～2 个候选写法**供用户挑；
6. **仍不许凭空编造** —— 候选值**必须来自该空间真实存在的枚举 / 成员 / 工作项**，不得虚构项目名、人名、分类选项；凡**不是直接来自用户材料**的信息（推断 / 经验值），一律按「材料铁律」标注「建议 / 推断」，并经用户全量确认后才能写入；
7. **不要反推或改动任何已有工作项** —— 本步只产出草稿，不写 TAPD。

#### 5.1·补充　描述结构化写法（**必读** —— 否则界面全挤成一行）

TAPD 的「详细描述」是**富文本**。只写纯文本 + `\n` 换行 → 后台会**并进同一个 `<p>`**，界面上所有内容挤成一行（2026-10-13 实测踩到）。必须写 HTML：

| 元素 | 用途 |
|---|---|
| `<p>…</p>` | 段落（每段一个） |
| `<strong>…</strong>` | **小标题加粗**（如 `【需求背景】`、`一、任务说明`、字段名） |
| `<ul><li>…</li></ul>` | **分条**（每条一个 `<li>`；支持 `<li><strong>标签：</strong>内容</li>`） |

**Story 描述模板（HTML）**

```html
<p><strong>【需求背景】</strong></p>
<ul>
  <li><strong>业务场景与问题：</strong>……</li>
  <li><strong>影响范围：</strong>……</li>
  <li><strong>解决问题后的价值：</strong>……</li>
</ul>
<p><strong>【需求描述】</strong></p>
<ul>
  <li><strong>面向角色：</strong>……</li>
  <li><strong>功能点 1【P0 必做】：</strong>规则描述（触发条件、处理逻辑、交互表现）</li>
  <li><strong>功能点 2【P1 应做】：</strong>规则描述</li>
  <li><strong>范围边界：</strong>✅ 本次需要实现……；❌ 本次不实现（Non-goals）……</li>
</ul>
<p><strong>【验收标准】</strong></p>
<ul>
  <li><strong>正常场景：</strong>……</li>
  <li><strong>边界/异常：</strong>……</li>
  <li><strong>数据/性能：</strong>……</li>
</ul>
<p><strong>【附录】</strong></p>
<ul><li><strong>PRD 文档：</strong>……</li></ul>
```

> 以上都是**无序**内容 → 用圆点列表，**不加 `（1）`**。只有像「操作步骤」「状态流转」这类**有先后**的部分，才另起编号段落：
> ```html
> <p><strong>操作步骤（按顺序）</strong></p>
> <p><strong>（1）创建迭代：</strong>……</p>
> <p><strong>（2）规划迭代：</strong>……</p>
> ```

**Task 描述模板（HTML）**

```html
<p><strong>一、任务说明</strong></p>
<ul>
  <li><strong>做什么：</strong>……</li>
  <li><strong>怎么做（技术要点）：</strong>……</li>
</ul>
<p><strong>二、完成定义（DoD）</strong></p>
<ul>
  <li>……</li>
  <li>……</li>
</ul>
<p><strong>三、依赖</strong></p>
<ul>
  <li><strong>依赖任务/接口：</strong>……</li>
  <li><strong>阻塞：</strong>……</li>
</ul>
```

> 若任务含**有先后的步骤**（如「创建 → 规划 → 关闭」「新建 → 处理 → 已解决…」），把它们单列一节，用**编号段落**（无圆点）：
> ```html
> <p><strong>操作步骤（按顺序）</strong></p>
> <p><strong>（1）创建迭代：</strong>……</p>
> <p><strong>（2）规划迭代：</strong>……</p>
> ```

**要点**

- **段落标题单独一段**：`<p><strong>小节名</strong></p>`，**不要**把小标题和正文塞进同一段；
- ⚠️ **无序 vs 有序 —— 编号只加给「有序」，且不能与圆点并存（2026-10-13 用户纠正）**：

  | 内容性质 | 写法 | 效果 |
  |---|---|---|
  | **无序**（并列、无先后） | `<ul><li>…</li></ul>` | 圆点 •　**不要再加 `（1）（2）（3）`** |
  | **有序**（步骤 / 流程 / 有先后） | **不用 `<ul>`**，改用无圆点的编号段落：`<p><strong>（1）小标题：</strong>正文</p>` | `（1）…`　无圆点 |

  **为什么**：`<ul><li>` 本身就渲染成圆点 •，那是"无序"标记；再叠 `（1）` 会变成「**• （1）做什么：**」双标记，既乱又语义矛盾。
  正确示例（有序）：
  ```html
  <p><strong>二、迭代操作步骤（按顺序）</strong></p>
  <p><strong>（1）创建迭代：</strong>点击迭代 → 新建 → 填写标题和起止时间 → 确认</p>
  <p><strong>（2）规划迭代：</strong>点击迭代右上角图标 → 规划 → 跳转页面后确认迭代 → 勾选工作项 → 规划到迭代</p>
  <p><strong>（3）关闭迭代：</strong>点击迭代右上角图标 → 关闭 → 确定</p>
  ```
- **已经带编号的不要重复编号**：如「第 0 章～第 8 章」「Q1～Q14」「功能点 1～7」本身即编号，仍用圆点列表呈现即可；
- **同一份描述内风格保持一致**（编号都用 `（1）` 或都不用；不混用 `1.` / `①`）；
- `&` 写成 `&amp;`（如「标题&amp;内容」）；`<`、`>` 同理转义；
- **创建后回读**：确认 description 里 `<p>` / `<strong>` / `<ul>` 都在（标签会被 TAPD 保留）；
- 脚本已加自动提示：描述缺 `<p>` / `<strong>` / `<ul>` 任一项 → 给出「缺少结构化标签」提示；
- **缺陷（Bug）的描述模板与 Story / Task 不同**（【环境】【版本】【复现步骤】【预期结果】【实际结果】【附件】六段），模板与 HTML 写法见「Bug（缺陷）」一节。

#### 5.3 用户改了任何字段 → **全量重展 + 再确认一次**（循环）

- 用户指出要改哪几处 → 覆盖对应字段 → **把整版草稿重新完整展示一遍**（**所有字段 + 描述全文都要重出**，不能只回显一句"已把 X 改成 Y"）→ 再次请用户确认；
- **⚠️ 本节覆盖此前"用户给了修改值就直接建、不再二次确认"的口径**（2026-10-13 用户更新要求）：**只要改过，就必须全量重展并重新确认**；
- 循环往复，直到用户明确表示**整版全部字段都没问题**。

#### 5.4 全部字段确认通过，才允许创建

**创建前必须同时满足三个条件：**

1. 该类型**全部必填字段都有值**（含详细描述，去标签后非空）；
2. 用户已对**整版全部字段（含描述全文）**明确确认通过；
3. `validate_required_fields.py` **退出码 = 0**。

**任一不满足即不得创建**，尤其注意：

- **用户只确认了其中一条**（如"第 1 条可以"）→ 不能建，其余条目仍需确认；
- **用户只说了"改一下 X"** → 那只是改稿指令，**不等于确认**，改完要重展再确认；
- **存在"枚举取值未命中已配置选项"的提示**（如优先级写了 `P5`、任务类型写了不存在的值）→ **必须先改成已有选项**（或由管理员配置新选项），**不得顶着提示创建** —— 详见「⛔ 字段配置 / 枚举值保护」；
- **用户没说"创建 / 确认无误"之前**，不得调用创建接口。

其他硬约束：缺字段不得创建；本步只涉及新建，若流程里包含**修改已有工作项**，仍须先跑 `update_change_guard.py`（见「已有值 / 自动字段保护」章节）。

### 第 6 步：创建

**只有满足下列全部条件才可调用创建接口：** ① 该类型全部必填字段（含详细描述）都有值；② 用户已对**整版全部字段**明确确认通过（**若用户改过任何字段，须先全量重展并重新确认**）；③ `validate_required_fields.py` 退出码 = 0。

满足后**整批一次创建**，不要"边校验边建"。

**创建前最后一道自检**：本次提交的数据**必须**已过校验（退出码 0）；未通过或有字段未经用户确认，一律不得调用创建接口。

### 第 7 步：创建后出「字段核对回执」（**必做**）

创建完成后，必须**按类型逐条**把刚写入的必填字段**实际值**列给用户核对 —— 因为"接口返回成功 ≠ 字段真写进去了"（见坑 10：传中文被静默写成 `0`）。

**做法：**

1. 用 `mcp__tapd__get_stories_or_tasks` 按 `id` 回读刚创建的每条工作项（`fields` 带上该类型的**全部必填字段**）；
2. 跑回执脚本生成对照表：

```bash
python "<skill目录>/scripts/creation_receipt.py" \
  --expected "<创建时提交的数据.json>" \
  --actual "<回读数据.json>" [更多回读文件...]
```

- 输出：逐条列出 `✓ 字段名  实际值`；有问题则标 `✗ 缺失（未填上）` 或 `✗ 预期「X」→ 实际「Y」`
- 退出码：`0`=全部正确 / `1`=有缺失或不一致 / `2`=输入错误
- 只给 `--actual` 也能用（只查"有没有填上"，不做预期比对）

3. **把回执原样发给用户**（含每条的 ID 与 TAPD 链接，方便点开核对）；
4. **回执里出现 ✗ 时**：用 `update_story_or_task` 修正 → **重跑回执** → 直到全绿再告知用户完成。

- 用户说**「创建 / 可以 / 没问题」且未提出任何修改** → 才可调用创建接口；
- 用户**指出要改哪几处**（哪怕只改一个字段） → 覆盖草稿 → **把整版草稿重新全量展示一遍**（所有字段 + 描述全文 + 层级 + 校验，**不能只回显"已把 X 改成 Y"**）→ **再次请用户确认** → 确认后才创建。

> ⚠️ 这里是 **2026-10-13 用户更新要求**，覆盖此前"给了修改值就直接建、不再二次确认"的口径：**改过就必须全量重展、重新确认**。

**改后重展的收尾话术：**


**要点**：把"要建什么"全量列清楚（全部字段 + 描述全文 + 层级）供用户核对，不能只说一句"校验通过"。

## 五、批量 / 复制场景（必须同样校验）

- **批量创建**：逐条校验，**逐条给出草稿值**（按 4.1 模板分组呈现）；推不出值的字段单独列在草稿下方（4.2），**不要整批停摆等追问**。整批校验通过 + 用户确认后才创建。
- **复制已有工作项**：不能因为"源数据是完整的"就跳过校验。复制时通常要改动父需求、处理人、时间，**这些恰恰是必填项**，一律按新数据重新校验。
- **从 Story 批量生成子任务**：父需求（`parent_id`）应自动带出，但任务类型/优先级/处理人/起止时间/预估工时仍需逐条确认。若用户说"照源数据的字段填"，就用源数据的值填好再校验，**不要留空**。

## 六、状态流转校验（**流转前必做**）

> **用户要求（2026-10-13）：流转状态时也要校验必填字段。** 有值的直接带出来**全量展示**给用户确认；没值的**先按经验拟一个建议值**，然后**全量展示给用户确认，确认通过后才能流转**。

### 6.1 为什么流转也要管

TAPD 的必填校验发生在**流转那一刻**（例如任务「未开始 → 进行中」强制 5 项）。界面上会弹窗让填，**但通过 MCP 流转时只会抛一个不友好的报错**，用户既不知道缺什么、也不知道该填什么。所以流转前先把必填项备齐、并让用户过一眼。

> **缺陷（Bug）流转同样要走本节流程**：取工作流时 `system` 传 `bug`；两空间的流转必填项已实测整理好，见「Bug（缺陷）」一节的流转必填表（36495762 与 32496738 要求不同）。

### 6.2 怎么取"这次流转要求哪些必填字段"

- 流转规则：`mcp__tapd__get_workflows_all_transitions`（`system: story`、`workitem_type_id` 按对象类型）→ 返回的每条流转里，**`Appendfield[].Notnull == "yes"` 的字段就是该流转的必填项**；
- 状态中英文对照：`mcp__tapd__get_workflows_status_map`。

> 已知（2026-10-13 实测，任务 `0035`）：状态只有 未开始/进行中/已完成；**「未开始→进行中」「→已完成」必填 5 项**＝处理人 + 任务类型 + 优先级 + 预计开始 + 预计结束；到「已完成」另需**登记工时**（`enable_add_timesheet`，系统项）。

### 6.3 执行步骤（四步，不得跳步）

1. **取规则** —— 调 `get_workflows_all_transitions` 并落盘，用脚本 `--list` 看该类型全部流转及各自必填项；
2. **取当前值** —— `mcp__tapd__get_stories_or_tasks` 按 `id` 回读该工作项（`fields` 带上这些必填字段）；
3. **跑脚本判定**：

```bash
# 先列出该类型全部流转与必填项：
python "<skill目录>/scripts/transition_guard.py" --workflow "wf.json" --list

# 再校验一条具体流转（空缺字段会标 ✗，退出码 1 = 不得流转）：
python "<skill目录>/scripts/transition_guard.py" --workflow "wf.json" --from "未开始" --to "进行中" --current "item.json" --suggest '{"due":"2026-10-16"}'
```

   - 退出码：`0`＝该流转必填项都有值；`1`＝**有缺失，不得流转**；`2`＝输入错误；
   - 输出含「字段｜标签｜当前值/建议值｜来源｜状态」，可直接拿去给用户确认。

4. **全量展示 + 等确认**（见 6.4）→ **确认通过后**才调用流转接口。

### 6.4 展示与确认（与创建同一套口径）

- **有值的字段** → 直接带出，来源标「当前值」；
- **没值的字段** → **先按经验 / 上下文拟一个建议值**，来源标「建议值（待你确认）」；**枚举字段只能取该空间已配置的选项**（见「⛔ 字段配置 / 枚举值保护」），拟不出就标「❓ 待你给」；
- **必须全量展示**：把该流转的**全部必填字段**（含系统项）列成一张表给用户；
- **用户改了任何字段 → 重出整张表再确认**（不许只回显"已把 X 改成 Y"，与创建流程同规则）。

**话术模板：**

```
即将流转：Task「开发-询价接口非必填改造」　未开始 → 进行中

| 字段 | 标签 | 当前值 / 建议值 | 来源 |
|---|---|---|---|
| owner | 处理人 | 张岩 | 当前值 |

```

### 6.5 硬约束

1. **必填项没备齐（或用户未确认整表）→ 不得流转**；
2. 若流转时**顺带要补写字段**，先跑 `update_change_guard.py`（补空可执行、覆盖需确认、系统自动字段不动）；
3. 流转会**自动写系统字段**（实际开始 / 完成时间等）—— 这是正常行为，**不要手工去写这些字段**；
4. 用户没说"确认 / 流转"之前，不得调用流转接口。

## 七、常见坑

1. **`category_id` 是任务上** —— 别把任务的"分类"当必填（它不是），任务必填的是 `custom_field_19`（任务类型）。
2. **`-1`（未分类）不算填了** —— 枚举字段选"未分类"视为缺失。
3. **`parent_id="0"` 不算填了** —— 代表没关联父需求。
4. **`effort` 是小时不是人天** —— **预估工时 > 24h 弹出醒目提示：「请与主管确认工时的合理性」**（≤24h 不提示；warning 不阻断，**允许存在超过 24h 的任务**——用户坚持即可放行）。
5. **日期格式必须是 `YYYY-MM-DD`** —— 传"10月15日""2026/10/15"都会被 TAPD 当无效值。
6. **Story 的父需求是 Feature、Task 的父需求是 Story** —— 隔层级别接错（Feature→Story→Task）。
7. **同性挂载是硬错误，不是"可接受写法"** —— **Story 的父需求不能是 Story，Task 的父需求不能是 Task**，也不能越级（Story 挂 Epic、Task 挂 Feature/Epic）。层级铁律见第 4 步；给待创建数据带上 `parent_type` 就能让脚本自动拦住，漏传则必须用 MCP 查一次父需求类型。
8. **Epic 不能有父需求** —— 它是顶层，`parent_id` 必须为空（传了 `parent_id` 会被判错，别照抄子级的写法）。
9. **别把"创建时"和"流转时"必填搞混** —— 流转时额外要求（如任务转"进行中"要求处理人等）不改变创建必填清单。
10. **详细描述别用空壳充数** —— `<p></p>` / `<p><br></p>` / `&nbsp;` 这类去标签后为空的，一律算缺失；必须写实际内容（背景 / 做什么 / 验收点）。**描述由 AI 先起草**（Story 四段 / Task 三段），不要留空让用户写。
11. **草稿必须全量展示，且改一处就要全量重展** —— 每次展示都要给全：**全部必填字段 + 详细描述全文 + 层级 + 校验结果**。用户改了任何字段（哪怕只改一个），**不能只回显"已把 X 改成 Y"**，要把整版重新完整贴一遍再请确认。
12. **未经全量确认不得创建** —— 用户只确认了部分条目、或只给了修改值，都不等于批准；**必须整版全部字段确认通过**才建（含 Epic / Feature / Story / Task / 缺陷五类）。
13. **标题不能只写"开发-""测试-"这类前缀** —— 至少要能看出具体做什么；脚本无法判断语义，遇到明显过短的标题会给出提示。
14. **`category_id` 创建时只能传选项 ID，不能传中文**（2026-10-13 实测踩到）—— 传"技术需求"会被**静默写成 `0`**（接口不报错，回读才发现像填了、其实没生效）。正确传法：技术需求=`1132496738001000029`；写错了再用 `update_story_or_task` 补。
15. **创建后要回读核验** —— 接口"返回成功"不等于字段真的写进去了（见第 14 条）。建议创建完按 id 拉一次，确认必填字段与层级（`path`/`level`）都对。
16. **不得改动 TAPD 已配置的字段名 / 枚举值** —— 枚举字段只能填**该空间已存在的选项**，不得自造（`P5`、`紧急`…）、不得改名、不得新增/删除选项。没有合适选项就**停下报告用户**，由管理员在 TAPD 界面配置；不要拿别的值顶替，也不要新建同名字段绕过。
17. **流转前也要校验必填** —— 见「六、状态流转校验」：先取该流转的必填项 + 回读当前值，有值直接带出、没值拟建议值，**全量展示并经用户确认后**才流转。
18. **删除必须先出「醒目警告 + 关联影响」再等确认** —— 见「⛔ 删除保护」。只问"要删吗"不行；批量删要**逐条**列影响；含糊的"嗯""看看"**不算确认**。
19. **不要冒用他人身份** —— 操作人 / 评论署名 / 工时登记人必须是**授权账号**（`get_current_user`）；但 `owner`、`developer`、需求提出方这类**业务字段可以填别人**，别混为一谈。
20. **别用"变通"绕过确认** —— 例如用改状态、改名、移出父级来替代删除，或用别的字段顶替不存在的枚举值 —— 都属于规避校验，禁止。
21. **详细描述必须写成 HTML 结构** —— 只写纯文本 + `\n` 换行会被 TAPD 并进**同一个 `<p>`**，界面上全挤成一行（2026-10-13 实测）。必须用 `<p>` 分段、`<strong>` 小标题加粗、`<ul><li>` 分条；模板见「5.1·补充　描述结构化写法」。脚本会对缺少这三类标签的描述给提示。
22. **描述里的 `&` / `<` / `>` 要转义** —— 写成 `&amp;` / `&lt;` / `&gt;`，否则富文本会解析异常或丢字。
23. **材料之外的信息必须经确认才能写入** —— 字段值与描述内容优先取自用户材料（对话内容 / 用户指定的文档 / TAPD 实数据）；靠推断、经验得出的值必须标「建议 / 推断」并经全量确认。**未经用户确认，任何写操作（创建 / 修改 / 流转 / 删除 / 评论 / 工时）都不得执行** —— 见「材料铁律」。
24. **缺陷（Bug）创建同样要走「草稿 → 确认 → 创建 → 回执」** —— 缺陷在两个空间都有，必填清单不同（36495762 生产缺陷处理：标题 + 6 项；32496738 需求池：**标题&内容 + 7 项 = 关联需求/严重程度/处理人/开发人员/缺陷类型/迭代/引入阶段**，手册第 4 章）；不走父需求层级校验，但需求池缺陷必须关联需求；确认铁律、材料铁律、账号铁律照样适用；**标题/描述全文与必填字段一次性全量确认**，用户改哪处整版重展再确认。
25. **修改缺陷、变更缺陷状态也必须先确认** —— `update_bug` 适用「已有值 / 自动字段保护」（覆盖已有值必须先回读展示"现在是 X 要改成 Y"）；缺陷流转必填项两空间不同（32496738 的「处理中」还要求处理人；两空间的「拒绝」流转都要求拒绝原因，字段 ID 不同：36495762=`custom_field_four`、32496738=`custom_field_two`），实测表见「Bug（缺陷）」一节；**每次流转前必须实查工作流**（配置可能被管理员随时调整），确认通过前不得调用接口。
26. **用户没说空间就先问，不得默认** —— 创建 / 修改 / 流转缺陷前，若用户未明确目标空间，必须先向用户确认（`36495762` 生产缺陷处理 / `32496738` 需求池）；两空间必填清单、流转必填、拒绝原因字段 ID 都不同，默认或猜错空间会导致整套校验失效。
27. **缺陷接口字段名与直觉不符，创建后必须回读** —— ①严重程度 `severity` 只收英文枚举（serious 等），传中文 / P1 无效；②缺陷类型=`bugtype`、引入阶段=`sourcephase`（标准字段，`cus_缺陷类型` 这类自定义字段写法无效）；③**关联需求不走 `story_id` / `parent_id`**（传了不生效），要用 `entity_relations`（source_type=bug, target_type=story）建立关联，且关联后 `story_id` 仍显示 null 属正常。三项都是静默失败——接口返回 success 但字段没写上，**必须回读核验并补齐**。
28. **不存在的枚举值创建和修改都不允许** —— 例：把缺陷严重程度改成 P2（severity 只有 致命/严重/一般/提示/建议）。**创建侧**由 `validate_required_fields.py` 拦（`--strict-enum` 阻断）；**修改侧**在 `update_change_guard.py` 分级之后，枚举目标值按「2.5）枚举实时读取」核对选项，**不在选项内即弹出提示、不得执行** —— 两种操作同一条红线。
29. **计划时间倒挂要醒目提醒，但用户坚持可放行** —— 任务：预计结束 ≥ 预计开始；Story：评审 ≤ 开发开始 ≤ 提测 ≤ 测试开始 ≤ 测试完成 ≤ 上线（字段 ID 见「时间顺序约束」节）。脚本给 `⏰ 时间顺序提醒`（不阻断、退出码仍 0），**必须在草稿 / 修改确认页醒目展示**；用户坚持原值则放行。修改场景同样适用。
30. **登记工时前后都要查当天合计，超 12h 醒目提示「请与主管确认工时的合理性」** —— 同一登记人同一花费日期「已有 + 拟登记」合计 >12h（`timesheet_guard.py` 校验，`get_timesheets` 拉已有）→ 醒目提示**请与主管确认工时的合理性**；如需调整可减少工时或分摊到其他日期；用户明确坚持原值才放行。**登记完成后还须强制复查**：重拉该登记人当天全空间所有工时重跑校验（别人可能刚好同天也登了），超 12h 同样醒目提醒——已入库记录的调整（`update_timesheets`）经用户确认后执行。工时是累计数据，**登记前后都要现查**。
31. **操作对象的人员与你不匹配 → 醒目提醒，用户强制可放行** —— 修改 / 流转 / 删除 Epic / Feature / Story / Task / 两空间缺陷前，回读对象跑 `owner_match_guard.py`：处理人 / 产品经理 / 测试人员 / 开发人员 / 需求提出方（缺陷提出方）**均 ≠ 当前账号** → 弹「该 XX 的人员跟你不匹配，确定要操作么？」+ 逐字段明细 + 本次改动明细；**任一人员字段匹配就不提醒**；用户强制要改才放行。
32. **工时审计数据不得手工转录摘抄** —— 全空间/多人工时扫描必须**按人逐个 `owner` 过滤拉取**（`get_timesheets` 按 owner 过滤返回该人完整数据，通常一页拉完），把接口返回直接程序化处理；**禁止把几百条混合数据手工誊写进中间文件**——2026-10-13 实测因转录丢条目导致漏报 1 人（郝亚军 09-16 16h）、误报 1 人（黎沅欣 10-10 实为 8h 被报 15h），被用户当场纠出。
33. **TAPD 工时记录的 `entity_type` 对 Story/Task 统一存为 `story`** —— 登记时传 `entity_type: task`、回读仍显示 `story`（接口行为，2026-10-13 实测：task `…1812` 的工时记录 entity_type=story，对象反查确认是 Task）。因此工时明细里显示 story **不代表对象一定是需求**；需要精确区分时用 `get_stories_or_tasks`（`entity_type: tasks`）按 ID 反查，不要直接向用户断言「这条挂在需求上」。
